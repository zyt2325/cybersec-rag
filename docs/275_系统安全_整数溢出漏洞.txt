整数溢出漏洞

一、基本概念  
1. 整数溢出是程序对有符号或无符号整数执行算术运算时，结果超出其数据类型可表示范围，导致值异常回绕的现象。  
2. 溢出本身不直接导致崩溃，但会引发后续逻辑错误，如内存越界、权限绕过或控制流劫持。  
3. C/C++等缺乏运行时整数边界检查的语言中，该漏洞尤为常见且危险。  
4. 与缓冲区溢出不同，整数溢出发生在算术计算阶段，常作为其他漏洞（如堆溢出）的前置触发条件。  

二、原理与关键机制  
1. 无符号整数溢出遵循模运算规则：例如 uint8_t 类型下 255 + 1 = 0（256 mod 256）。  
2. 有符号整数溢出在C标准中属于未定义行为（UB），编译器可任意优化，导致跨平台行为不一致。  
3. 溢出常发生在分配内存前的大小计算中，如 size = len1 + len2，当二者之和回绕为小值，导致分配空间不足。  
4. 编译器优化可能删除开发者意图的溢出检测代码，尤其在启用 -O2 或更高优化级别时。  

三、典型类型与常见问题  
1. 加法/乘法溢出：用于计算数组索引、内存分配尺寸或循环边界时，产生远小于预期的值。  
2. 减法下溢：无符号数 a - b 中若 a < b，结果回绕为极大正数，可能触发越界读写。  
3. 符号转换溢出：将有符号负值（如 -1）赋给无符号变量，变为极大正值（如 UINT_MAX），破坏逻辑判断。  
4. 循环计数器溢出：for (unsigned int i = len; i >= 0; i--) 因无符号特性导致无限循环或跳变。  
5. 长度字段校验失效：协议解析中，攻击者构造超大长度字段，使校验计算溢出后通过检查。  

四、防御措施与实践建议  
1. 使用编译器内置检查：启用 Clang 的 -fsanitize=integer 或 GCC 的 -fanalyzer（有限支持），在开发阶段捕获溢出。  
2. 采用安全算术库：如 OpenBSD 的 explicit_bzero() 配套的 safe_add/safe_mul，或 C11 标准的 _Generic 宏封装。  
3. 关键计算前进行显式范围校验：例如分配前验证 len1 <= SIZE_MAX - len2，而非依赖事后检查。  
4. 优先使用 size_t 处理内存相关尺寸，避免混用 signed/unsigned 类型，禁止隐式类型转换。  
5. 在协议解析与驱动开发等高危场景，对所有外部输入的整数字段执行双向校验（最小值与最大值）。  
6. 静态分析工具集成：将 Infer、CodeQL 或 Semmle 规则纳入 CI 流程，识别潜在溢出路径与危险模式。
