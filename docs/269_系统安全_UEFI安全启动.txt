UEFI安全启动

一、基本概念  
1. UEFI安全启动是UEFI固件中强制执行的启动验证机制，确保仅加载经可信密钥签名的引导组件。  
2. 它替代传统BIOS的无验证启动流程，从固件层建立信任链起点（Root of Trust），覆盖引导加载程序、驱动和OS内核。  
3. 安全启动依赖预置在固件中的平台密钥（PK）、密钥交换密钥（KEK）和签名数据库（db/dbx），构成分级密钥管理体系。  
4. 启用后，固件在每个启动阶段校验下一阶段二进制的数字签名，任一环节验证失败即中止启动并报错。  
5. 该机制不提供加密保护，仅保证代码完整性与来源可信性，不防止运行时内存篡改或侧信道攻击。

二、原理与关键机制  
1. 启动过程遵循“信任链传递”：固件验证Boot Manager签名→Boot Manager验证OS Loader签名→Loader验证内核签名。  
2. 签名验证使用X.509证书体系，支持SHA-256哈希与RSA-2048/3072或ECDSA-P256签名算法，禁用弱算法（如SHA-1、RSA-1024）。  
3. db数据库存储允许执行的签名公钥或哈希值；dbx数据库存储已吊销的签名或哈希，优先级高于db。  
4. PK控制KEK更新权限，KEK控制db/dbx更新权限，形成密钥策略隔离，防止低权限密钥越权修改高权限策略。  
5. 固件实现必须符合UEFI规范2.7及以上版本要求，且需通过TPM 2.0可选扩展支持启动日志度量（Event Log）。

三、典型类型与常见问题  
1. 厂商锁定型：OEM预置唯一PK，用户无法替换，导致Linux发行版或自定义内核无法启动，除非禁用安全启动。  
2. 密钥管理失当：KEK或db被恶意固件更新劫持，攻击者注入恶意签名至db或清除dbx条目，绕过验证。  
3. 签名绕过漏洞：部分UEFI实现存在SMM内存映射缺陷或Boot Services调用逻辑错误，可被用于执行未签名代码。  
4. 驱动签名缺失：第三方硬件驱动未获微软WHQL签名或未加入厂商db，启用安全启动后设备无法初始化。  
5. 固件更新漏洞：带漏洞的UEFI更新包若被签名且载入db，可能引入持久化启动级后门，如LoJax类攻击。

四、防御措施与实践建议  
1. 企业部署应统一签发并分发内部PK/KEK，通过UEFI配置工具批量注入，禁用默认OEM PK以消除供应链单点风险。  
2. 定期轮换KEK并审计db/dbx内容，使用signtool或efitools验证关键组件签名有效性，比对固件导出的签名列表。  
3. 在开发环境中启用“用户模式”安全启动（Custom Mode），配合Secure Boot Debug Policy捕获验证失败详情。  
4. 对于Linux系统，采用shim+GRUB2+内核多级签名方案，shim须经微软认证并嵌入MOK机制支持自定义密钥。  
5. 禁用不必要的UEFI启动服务（如Network Stack、HTTP Boot），缩小攻击面；启用TPM 2.0事件日志并远程验证启动完整性。  
6. 固件更新前须校验供应商签名及哈希值，避免通过非安全通道（如HTTP）下载更新包，防范中间人篡改。
