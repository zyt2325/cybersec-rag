OAuth2授权漏洞

一、基本概念  
1. OAuth2是用于第三方应用获取有限访问权限的开放授权框架，不传输用户凭证。  
2. 授权过程涉及资源所有者、客户端、授权服务器和资源服务器四个核心角色。  
3. 授权码模式（Authorization Code Flow）是Web应用最常用且相对安全的流程。  
4. 访问令牌（Access Token）是短期凭据，代表客户端对特定资源的访问权限。  
5. 刷新令牌（Refresh Token）用于在访问令牌过期后获取新令牌，需严格保护。  

二、原理与关键机制  
1. 授权端点（/authorize）负责用户认证与授权决策，返回授权码而非令牌。  
2. 令牌端点（/token）验证授权码、客户端身份及重定向URI后颁发访问令牌。  
3. PKCE（RFC 7636）通过代码挑战/验证机制防止授权码拦截攻击。  
4. 重定向URI必须严格校验，仅允许预注册的白名单地址，防止开放重定向。  
5. 客户端必须使用client_secret或PKCE证明自身身份，避免伪造客户端冒用。  
6. 访问令牌应绑定客户端ID、作用域（scope）、受众（audience）及绑定设备指纹等上下文信息。  

三、典型类型与常见问题  
1. 授权码劫持：攻击者诱骗用户点击恶意链接，截获授权码并兑换为访问令牌。  
2. 开放重定向滥用：授权服务器未校验重定向URI，导致授权码被重定向至攻击者控制的域名。  
3. 客户端凭证泄露：单页应用（SPA）将client_secret硬编码在前端，造成凭证暴露。  
4. Scope过度授权：应用请求超出实际需要的权限（如email+profile+contacts），扩大泄露影响面。  
5. 刷新令牌未绑定会话：刷新令牌长期有效且未绑定IP或设备，遭窃后可无限续期访问令牌。  
6. 隐式流（Implicit Flow）误用：已废弃于现代Web应用，因令牌直接在URL中传递易被日志或代理截获。  

四、防御措施与实践建议  
1. Web后端应用必须使用授权码+PKCE流程，禁用隐式流与密码模式。  
2. 所有客户端必须预注册重定向URI，且服务端执行精确匹配（含协议、主机、路径、查询参数）。  
3. SPA类应用应采用无密钥模式（PKCE mandatory），禁止存储client_secret，令牌存于内存而非localStorage。  
4. 访问令牌设短有效期（≤1小时），配合强绑定策略（如aud、cid、jti、绑定IP/User-Agent）。  
5. 刷新令牌须一次性使用、绑定设备指纹、设置较短有效期，并在每次使用后轮换新令牌。  
6. 授权服务器应记录授权决策日志，监控异常授权行为（如高频scope变更、跨地域令牌兑换）。
