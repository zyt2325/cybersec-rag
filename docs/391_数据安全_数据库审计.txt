数据库审计

一、基本概念  
1. 数据库审计是指对数据库访问行为进行系统性记录、监控与分析的过程，用于保障数据完整性、机密性和合规性。  
2. 审计对象包括用户登录/登出、SQL语句执行（如SELECT、INSERT、UPDATE、DELETE）、权限变更、存储过程调用等关键操作。  
3. 审计日志是核心输出，需包含时间戳、源IP、客户端程序、数据库用户、执行语句摘要、影响行数及返回状态码等结构化字段。  
4. 合规驱动是主要动因，如等保2.0要求三级及以上系统必须启用数据库审计功能，并保留日志不少于180天。  

二、原理与关键机制  
1. 审计通常通过代理模式（部署独立审计网关）或内嵌模式（利用数据库原生审计模块，如Oracle Unified Audit、MySQL audit_log插件）实现。  
2. 基于策略的实时匹配机制：预设规则（如“非授权用户访问敏感表”“凌晨2点至5点的批量导出操作”）触发日志记录与告警。  
3. 语句解析与脱敏处理：对SQL文本进行语法解析提取关键元素（目标表、列、谓词），对敏感字段值（如身份证号）自动掩码后记录。  
4. 日志防篡改设计：采用只追加写入、数字签名、异地同步或硬件安全模块（HSM）保护审计日志存储完整性。  

三、典型类型与常见问题  
1. 基于网络流量的旁路审计：镜像数据库通信流量进行协议解析，不依赖数据库配置，但无法识别加密连接中的SQL内容。  
2. 基于数据库日志的审计：解析事务日志（如SQL Server LDF、PostgreSQL WAL），可捕获物理层变更，但开销大且难以关联业务上下文。  
3. 权限滥用风险：高权限账号（如DBA）操作常被默认豁免审计，导致内部越权行为难以追溯。  
4. 性能瓶颈：全量SQL审计在高并发场景下可能引发延迟升高或日志丢失，尤其未启用异步写入与缓冲机制时。  
5. 日志爆炸与噪声：未过滤冗余操作（如健康检查心跳查询）导致日志量激增，掩盖真实威胁线索。  

四、防御措施与实践建议  
1. 实施最小权限审计策略：仅对敏感表（含PII/PHI字段）、特权操作（GRANT/REVOKE）、异常时段行为启用细粒度审计。  
2. 部署审计日志集中管理平台：使用SIEM工具（如Splunk、ELK）统一采集、归一化解析并设置动态基线告警（如单用户单日UPDATE次数突增300%）。  
3. 强制启用会话级上下文绑定：将数据库会话ID、应用服务名、前端用户标识（如HTTP Header中的X-User-ID）注入审计日志，支撑跨层溯源。  
4. 定期执行审计有效性验证：通过模拟测试用例（如触发预设违规规则）验证日志生成、传输、存储与告警链路是否完整可用。  
5. 结合数据库防火墙（DBFW）联动：将审计发现的可疑行为（如SQL注入特征语句）实时同步至DBFW实施连接阻断。
