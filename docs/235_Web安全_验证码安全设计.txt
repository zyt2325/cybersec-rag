验证码安全设计

一、基本概念  
1. 验证码（CAPTCHA）是区分人类用户与自动化程序的挑战-响应机制，核心目标是阻断批量注册、暴力登录等自动化攻击。  
2. 其安全性依赖于“人类易解、机器难解”的认知差异，而非加密强度或密钥保密性。  
3. 验证码属于应用层访问控制辅助手段，不能替代身份认证主流程（如密码、多因素认证）。  
4. 合法使用需兼顾可访问性，WCAG 2.1要求提供音频替代方案及足够对比度文本，避免歧视残障用户。  

二、原理与关键机制  
1. 信息熵设计：字符集大小、长度、干扰线/点密度共同决定破解难度，低熵验证码易被OCR或模板匹配攻破。  
2. 会话绑定：服务端必须将验证码Token与用户会话ID强绑定，并在验证后立即失效，防止重放与跨会话复用。  
3. 时间窗口限制：验证码有效期通常设为120–300秒，超时即销毁服务端存储的校验状态，阻断延迟提交。  
4. 无状态生成：前端不应缓存或暴露原始验证码明文，服务端应基于随机种子+时间戳生成可验证哈希，避免客户端篡改。  

三、典型类型与常见问题  
1. 文本型验证码：易受深度学习OCR（如CRNN模型）识别，尤其当字体规则、背景简单时准确率超95%。  
2. 图像分类型：要求用户选择含交通灯、公交车等指定物体的图片，但对抗样本可误导模型输出错误标签。  
3. 行为式验证码（如reCAPTCHA v3）：采集鼠标轨迹、点击时序等生物特征，存在隐私合规风险及浏览器指纹追踪隐患。  
4. 逻辑题型（如“3+5=？”）：若服务端未动态生成数学表达式，易被正则匹配或固定答案表穷举破解。  
5. 静态图片复用：同一验证码图片被多次分发，导致离线打码平台可构建识别库，实现批量自动识别。  

四、防御措施与实践建议  
1. 采用服务端动态生成+一次一密策略：每次请求生成唯一Token，校验后立即清除Redis中对应键值对。  
2. 集成风险评估：结合IP信誉库、设备指纹、请求频次等维度，在触发阈值时升级验证码难度（如从文本切换至滑块）。  
3. 禁用客户端校验：所有逻辑必须在服务端完成，前端仅负责渲染与提交，防止绕过JS验证直接调用API。  
4. 定期更新验证码引擎：每6个月更换字体库、干扰算法及噪声参数，避免攻击者建立稳定识别模型。  
5. 设置失败熔断：单一会话连续3次验证码错误即锁定该会话15分钟，并记录日志供安全分析。  
6. 避免在登录失败后重复使用同一验证码，须强制刷新并生成新Token，切断暴力枚举路径。
