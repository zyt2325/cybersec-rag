GraphQL安全

一、基本概念  
1. GraphQL是一种用于API的查询语言和运行时，允许客户端精确指定所需数据字段。  
2. 与REST不同，GraphQL通常通过单个端点（如/graphql）处理所有请求，使用POST方法提交查询。  
3. 其核心组件包括Schema（类型定义）、Resolver（数据获取逻辑）和Query/Mutation/Subscription操作类型。  
4. Schema由开发者显式定义，包含类型、字段、参数及权限约束，是服务端安全策略的重要基础。  
5. GraphQL本身不内置认证、授权或速率限制机制，需由实现框架或上层服务补充。

二、原理与关键机制  
1. 查询解析阶段将字符串查询编译为AST（抽象语法树），校验语法、类型兼容性与字段存在性。  
2. 执行引擎按AST深度优先遍历，逐字段调用对应Resolver函数，支持嵌套字段并行解析。  
3. Introspection机制默认启用，允许客户端通过__schema查询获取完整Schema结构，含所有类型与字段。  
4. 字段级权限需在Resolver中手动实现，无全局字段访问控制钩子，易因疏漏导致越权。  
5. 查询复杂度未被Schema原生约束，深层嵌套或大列表返回可能引发资源耗尽。

三、典型类型与常见问题  
1. 过度获取：客户端可自由组合字段，无意中拉取敏感字段（如user.passwordHash），若Resolver未过滤则直接暴露。  
2. 深度嵌套攻击：构造高深度查询（如user{posts{comments{author{posts{...}}}）触发栈溢出或超时。  
3. 复杂度爆炸：利用字段返回列表+嵌套，使查询计算量呈指数增长（如N个用户各查M条评论）。  
4. Introspection滥用：攻击者利用默认开启的内省接口枚举全部类型、字段、参数，辅助探测业务逻辑与数据模型。  
5. 错误信息泄露：开发环境返回详细堆栈、数据库错误或字段不存在提示，暴露后端技术栈与Schema细节。

四、防御措施与实践建议  
1. 生产环境禁用Introspection，或通过中间件拦截__schema等内省查询，仅允许可信来源访问。  
2. 实施查询复杂度限制：为每个字段配置权重，拒绝总分超阈值（如1000）的请求，避免暴力估算。  
3. 强制字段级访问控制：在每个敏感字段的Resolver中验证用户权限，禁止依赖前置层级的粗粒度检查。  
4. 关闭调试模式，自定义错误响应：生产环境返回通用错误码，隐藏堆栈、字段名、数据库细节。  
5. 部署WAF规则识别异常GraphQL特征：如深度>7的嵌套、单次请求字段数>50、含可疑关键字的变量名。  
6. 使用 persisted queries：预注册合法查询ID，服务端仅执行白名单中的查询，阻断任意动态查询注入。
