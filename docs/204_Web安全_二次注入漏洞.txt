二次注入漏洞

一、基本概念  
1. 二次注入是一种SQL注入变体，攻击者输入的恶意数据未在首次入库时触发执行，而是在后续业务逻辑中被拼接进新SQL语句时才被执行。  
2. 与一次注入不同，其危害不体现于初始输入点，而隐藏在数据读取、组合、重用等下游操作环节。  
3. 漏洞成因本质是“输入污染+上下文误信”，即数据库将用户输入当作可信数据存储，应用层后续调用时未做上下文适配的转义或参数化处理。  
4. 常见于多步骤业务流程，如用户注册信息存入数据库后，在后台报表生成、日志审计、消息推送等场景中被再次查询并拼接使用。

二、原理与关键机制  
1. 攻击者提交含SQL元字符（如单引号、分号、注释符）的字符串，经简单过滤或无害化处理后写入数据库，表面看似安全。  
2. 应用在后续功能中从数据库读取该字段值，未识别其原始上下文，直接将其拼接到新的SQL语句中（如WHERE子句或ORDER BY后）。  
3. 数据库引擎解析新SQL时，原存储的恶意片段被当作语法结构执行，绕过首次输入校验。  
4. 关键触发条件是：数据跨上下文复用 + 缺乏按目标上下文重新编码/参数化 + 服务端未区分“数据”与“代码”语义。

三、典型类型与常见问题  
1. 用户资料字段二次注入：如昵称字段存入' OR '1'='1，后续在“按昵称统计活跃度”SQL中被拼接导致条件恒真。  
2. 日志/审计模块注入：管理员导出操作日志时，将数据库中已存的用户IP或UA字段直接拼入SELECT语句，引发注入。  
3. 消息模板注入：系统读取数据库中预设的通知模板内容（含变量占位符），若模板本身被篡改含SQL片段，渲染时触发执行。  
4. 多语言环境下的编码混淆：UTF-8宽字节或GBK双字节截断残留，使部分过滤失效，为二次注入提供编码层面入口。  
5. ORM框架误用：开发者调用raw()或execute()方法时，将从数据库读取的字符串直接传入，未启用参数绑定。

四、防御措施与实践建议  
1. 坚持上下文敏感防御：对任何从数据库读取的数据，在用于SQL拼接前必须按当前SQL上下文重新进行参数化（如使用PreparedStatement）或转义。  
2. 实施最小权限数据访问：业务代码读取数据库字段时，仅查询必需字段，避免SELECT *，减少污染数据暴露面。  
3. 引入数据标记机制：对入库数据标注来源与信任等级，下游使用时强制校验标记，未标记或低信任数据禁止参与动态SQL构造。  
4. 统一使用参数化查询：所有SQL执行路径（包括ORM的原生查询接口）必须采用绑定参数，禁用字符串格式化拼接。  
5. 对历史数据清洗与加固：对已存在的用户输入字段批量扫描特殊字符组合，结合业务语义评估风险，必要时加字段级白名单约束。  
6. 在Web应用防火墙（WAF）策略中增加二次注入特征检测规则，如匹配“从DB读取→拼接→执行”行为链的响应模式。
