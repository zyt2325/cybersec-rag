数据湖安全

一、基本概念  
1. 数据湖是集中存储原始结构化、半结构化和非结构化数据的可扩展存储系统，通常基于对象存储（如S3、ADLS）构建。  
2. 数据湖本身不内置访问控制或加密机制，其安全性高度依赖外部策略、元数据管理与计算引擎协同保障。  
3. 与数据仓库不同，数据湖缺乏强模式约束和预定义权限模型，导致敏感数据易被误暴露或越权访问。  
4. 数据湖中数据常跨多租户、多业务线共享，元数据与实际数据物理分离，加剧权限治理复杂度。  

二、原理与关键机制  
1. 基于策略的访问控制（PBAC）是主流机制，通过统一策略引擎（如Apache Ranger、AWS Lake Formation）动态评估用户属性、资源标签与环境条件。  
2. 元数据目录（如AWS Glue Catalog、Delta Lake Metastore）承担权限映射枢纽角色，需强制启用细粒度读/写/描述权限绑定。  
3. 数据虚拟化层（如Trino、Presto）在查询执行时实施行级与列级过滤，避免原始数据全量下推至计算节点。  
4. 静态数据加密（AES-256）与传输中加密（TLS 1.2+）为强制基线要求，密钥须由HSM或云KMS托管，禁止硬编码密钥。  

三、典型类型与常见问题  
1. 云原生数据湖（如AWS Lake Formation架构）易因S3存储桶策略配置错误导致公开可读，引发大规模数据泄露。  
2. 混合部署场景下，本地Kerberos认证与云IAM角色信任链断裂，造成身份断言失效与权限提升风险。  
3. 自动化ETL作业常以高权限服务账户运行，若未实施最小权限原则，可能被横向利用窃取全湖数据。  
4. 数据血缘缺失导致无法追溯敏感字段来源，合规审计（如GDPR、等保2.0）难以验证脱敏与访问日志完整性。  

四、防御措施与实践建议  
1. 强制启用存储层默认加密，并对每个S3/ADLS容器配置显式拒绝公共访问策略及跨区域复制限制。  
2. 实施基于标签的自动化分类分级：利用Amazon Macie或Azure Purview识别PII/PHI字段，自动打标并触发策略更新。  
3. 所有SQL查询必须经由代理层（如Starburst Gateway）路由，禁用直连底层存储，确保所有访问留痕且受RLS/CLS控制。  
4. 定期执行权限稽核：使用Lake Formation Permissions API或Ranger审计日志，识别90天未使用的权限并自动回收。  
5. ETL作业运行时注入临时凭证而非长期密钥，结合短期会话令牌（STS AssumeRole）与资源级限定策略（如仅允许访问指定前缀路径）。  
6. 构建不可篡改的审计流水线：将所有访问日志实时写入专用只写存储桶，启用S3 Object Lock合规模式保留至少180天。
