JWT令牌安全  
一、基本概念  
1. JWT（JSON Web Token）是一种开放标准（RFC 7519），用于在各方之间安全传递声明（claims）的紧凑、自包含的URL安全字符串。  
2. 由三部分组成：Base64Url编码的Header、Payload和Signature，以英文句点分隔，如xxx.yyy.zzz。  
3. Header定义签名算法（如HS256、RS256）及令牌类型；Payload携带声明（注册、公共、私有）；Signature验证完整性和来源。  
4. JWT可被无状态使用，常用于OAuth 2.0访问令牌、会话管理及微服务间身份断言。  
5. 不同于传统session，JWT本身不依赖服务端存储，但其有效性校验仍需服务端执行密钥验证与声明检查。  

二、原理与关键机制  
1. 签名机制确保完整性：服务端使用密钥（对称）或私钥（非对称）对Header+Payload的哈希值生成签名，接收方用对应密钥验证。  
2. alg字段在Header中指定签名算法，若服务端未严格校验该字段，可能引发算法混淆攻击（如将RS256误当作HS256处理）。  
3. Payload中的exp（过期时间）、nbf（生效前时间）、iat（签发时间）等注册声明由服务端强制校验，缺失校验将导致令牌长期有效。  
4. 公共声明可自定义，但必须避免敏感信息明文存储；私有声明需双方约定且不公开语义。  
5. JWT不加密——除非使用JWE（JSON Web Encryption），否则Payload为Base64Url编码，可被任意解码，不可存放密码、密钥等机密数据。  

三、典型类型与常见问题  
1. HS256密钥强度不足或硬编码在客户端，易被逆向提取后伪造合法令牌。  
2. 服务端未校验alg=none或允许空签名，导致攻击者构造无签名令牌绕过验证。  
3. 忽略aud（受众）、iss（签发者）声明校验，使令牌可在不同应用或租户间非法复用。  
4. 过期令牌未加入黑名单（如Redis缓存），且缺乏主动吊销机制，无法应对密钥泄露或用户登出场景。  
5. 将JWT存于localStorage易受XSS窃取；存于HttpOnly Cookie虽防XSS但需同步防范CSRF。  

四、防御措施与实践建议  
1. 强制校验Header中alg字段，禁用none算法，仅允许白名单内的签名算法（如RS256、ES256），并使用独立库（如python-jose）而非手动解析。  
2. 服务端必须验证exp、nbf、iat、iss、aud等关键声明，且采用严格时间容差（≤1秒），拒绝已过期或未生效令牌。  
3. 使用非对称签名（RS256/ES256）替代HS256，私钥严格保护，公钥通过JWKS端点动态分发并定期轮换。  
4. 敏感操作前二次验证（如支付需短信确认），避免仅依赖JWT完成高危动作；短期令牌（如15分钟）配合刷新令牌机制。  
5. JWT应通过Secure+HttpOnly+SameSite=Strict Cookie传输，前端禁止读取；若必须JS访问，采用短生命周期+绑定User-Agent/IP指纹。  
6. 实施令牌吊销机制：维护短时效黑名单（如Redis中存储jti+exp），或采用分布式会话ID映射方式实现细粒度失效控制。
