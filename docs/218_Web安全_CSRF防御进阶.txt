CSRF防御进阶

一、基本概念  
1. CSRF（跨站请求伪造）是攻击者诱使已认证用户在不知情下向目标站点提交恶意请求的攻击方式。  
2. 攻击成功依赖三个条件：用户已登录目标站点、浏览器自动携带会话凭证（如Cookie）、目标站点未校验请求来源合法性。  
3. 与XSS不同，CSRF不窃取用户数据，而是劫持用户身份执行非预期操作，如转账、改密、删资源。  
4. 本质是服务端将“拥有有效会话”等同于“用户主动发起请求”，忽略了请求真实意图的验证。

二、原理与关键机制  
1. 浏览器同源策略不限制跨域请求的发起，仅限制响应读取，因此GET/POST表单或图片标签均可触发跨域请求。  
2. 服务端依赖Cookie自动附带机制维持会话，但无法区分该Cookie是由用户主动导航还是第三方页面诱导发送。  
3. 关键漏洞点在于服务端未对状态变更请求（如POST/PUT/DELETE）强制绑定一次性、不可预测、绑定用户上下文的校验凭证。  
4. CSRF令牌必须具备唯一性、时效性、绑定性：每个会话或每次请求生成新值，且与用户ID、时间戳、随机盐值强关联。

三、典型类型与常见问题  
1. GET型CSRF易被忽视，因URL参数可被嵌入img/script标签，导致无交互式触发（如删除操作暴露于GET接口）。  
2. “双Cookie验证”若仅比对Cookie与请求头中同名值，而未绑定用户会话ID或签名，易遭重放或覆盖绕过。  
3. Referer检查不可靠：部分浏览器或代理可能屏蔽Referer；HTTPS页面跳转至HTTP时Referer清空；企业防火墙常过滤该字段。  
4. 自定义Header防御（如X-Requested-With）仅对XMLHttpRequest/XHR有效，无法防护表单提交、fetch无headers配置或Flash等旧技术发起的请求。

四、防御措施与实践建议  
1. 强制使用Synchronizer Token Pattern：在所有状态变更请求中校验服务端签发的CSRF令牌，令牌存储于HttpOnly Cookie并同步输出至表单隐藏域或API请求头。  
2. 采用SameSite Cookie属性，严格设置为Strict或Lax（推荐Lax+POST降级处理），阻止跨站上下文中Cookie自动发送。  
3. 对高危操作实施二次验证：要求输入密码、短信验证码或U2F/WebAuthn确认，不替代CSRF令牌，而是纵深防御补充。  
4. 实施精确的Origin校验：验证Origin头是否匹配白名单域名，注意兼容性（IE不支持Origin），需与Referer协同作为fallback。  
5. 避免在GET请求中执行状态变更，RESTful设计应严格遵循GET幂等原则，敏感操作统一使用POST/PUT/DELETE并强制令牌校验。  
6. 前端框架集成防护：如Angular自动注入XSRF-TOKEN Cookie并添加X-XSRF-TOKEN头；React应用需显式管理令牌生命周期与请求拦截。
