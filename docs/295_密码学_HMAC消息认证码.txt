HMAC消息认证码  
一、基本概念  
1. HMAC是基于哈希函数构造的消息认证码，用于验证消息完整性与来源真实性。  
2. 它采用密钥与消息共同输入哈希函数的方式，输出固定长度的认证标签。  
3. HMAC不是加密算法，不提供机密性，仅保障消息未被篡改且出自合法持有密钥方。  
4. RFC 2104定义其标准结构，支持任意迭代型哈希函数（如SHA-256、SHA-3、MD5等）。  
5. 密钥需保密且具备足够熵值，长度建议不低于哈希输出长度，或至少128位。  

二、原理与关键机制  
1. HMAC通过两次哈希嵌套实现：先用密钥异或ipad后与消息拼接哈希，再用密钥异或opad后与上步结果拼接哈希。  
2. ipad和opad为固定常量（0x36和0x5C重复填充至哈希块长），防止长度扩展攻击破坏密钥隔离性。  
3. 密钥被隐式“包裹”在哈希计算内部，避免直接作为哈希输入导致的密钥泄露风险。  
4. 即使底层哈希函数存在碰撞弱点（如MD5），HMAC仍可维持PRF安全性，前提是密钥未知。  
5. 其安全性可归约证明：若HMAC不可伪造，则底层哈希函数必须满足抗碰撞性与伪随机性。  

三、典型类型与常见问题  
1. HMAC-SHA256为当前主流选择，兼顾性能与安全性；HMAC-MD5已禁用于高安全场景，因MD5碰撞易构造。  
2. 密钥复用风险：同一密钥用于不同协议或上下文，可能引发跨协议密钥推导攻击。  
3. 截断使用不当：截短HMAC输出（如取前8字节）会显著降低暴力猜测成功率，应保留至少128位有效输出。  
4. 时间侧信道漏洞：朴素的字节逐位比较验证函数可能导致时序差异，暴露认证标签部分信息。  
5. 初始化向量缺失：HMAC本身无IV，若在需要随机化的场景（如重放防护）中未结合nonce或计数器，将丧失新鲜性保障。  

四、防御措施与实践建议  
1. 使用HMAC-SHA256或HMAC-SHA384，禁用HMAC-MD5、HMAC-SHA1于新系统。  
2. 密钥须由密码学安全随机数生成器产生，长度等于或大于哈希输出长度（如SHA256对应32字节）。  
3. 验证时采用恒定时间比较函数（如OpenSSL的CRYPTO_memcmp），避免时序旁路。  
4. 每个应用逻辑场景分配独立密钥，禁止跨服务、跨算法共享同一密钥材料。  
5. 在协议设计中将HMAC与序列号、时间戳或随机nonce组合使用，防范重放攻击。  
6. 对HMAC输出执行Base64URL编码而非十六进制，减少传输体积并规避大小写歧义问题。
