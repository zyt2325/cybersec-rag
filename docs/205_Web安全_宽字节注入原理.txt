宽字节注入原理

一、基本概念  
1. 宽字节注入是利用多字节字符编码（如GBK、GB2312）中高位字节与转义字符交互引发的SQL注入变种。  
2. 核心前提是Web应用使用宽字节编码但未正确处理MySQL的sql_mode或客户端字符集配置。  
3. 区别于普通注入，其触发依赖字符集不一致导致的“逃逸式”转义失效，而非单纯输入过滤绕过。  
4. 常见于PHP+MySQL组合中，当mysql_query()等函数执行前未显式设置连接层字符集时风险显著升高。  

二、原理与关键机制  
1. MySQL在宽字节模式下将\x5C（反斜杠）与后续字节组合为合法汉字，使单引号前的转义符被“吞掉”。  
2. 例如GBK编码中\xA1\x5C构成一个汉字，导致\x27\x5C\x27（'\'）被解析为'＋[汉字]＋'，破坏转义逻辑。  
3. 关键条件包括：PHP使用addslashes()等基于ASCII的转义函数，且数据库连接未强制SET NAMES gbk。  
4. MySQL服务端默认字符集（如latin1）与客户端声明字符集（如gbk）不匹配时，会触发隐式转换漏洞链。  
5. 宽字节注入本质是字符集解析歧义引发的语义错位，非语法层面的SQL结构篡改。  

三、典型类型与常见问题  
1. 单引号逃逸型：通过构造\xA1\x27等双字节序列使addslashes()插入的\x5C被合并，恢复闭合能力。  
2. 注释符干扰型：利用宽字节截断注释符（如\x5C\x23）导致#后语句未被注释，延续恶意SQL逻辑。  
3. 多字节编码混淆：GB2312、GBK、Big5均存在类似问题，但UTF-8因无合法\x5C组合体故天然免疫。  
4. PDO预处理失效场景：若仅用PDO::ATTR_EMULATE_PREPARES=true且未绑定字符集，仍可能触发宽字节逃逸。  
5. WAF绕过关联：部分基于正则的WAF未覆盖宽字节特征码，误判\xA1\x27为正常文本而放行。  

四、防御措施与实践建议  
1. 统一字符集：PHP连接MySQL时必须显式执行SET NAMES utf8mb4或设置PDO::MYSQL_ATTR_INIT_COMMAND。  
2. 禁用addslashes()：改用mysqli_real_escape_string()并传入有效连接句柄，确保转义适配当前连接字符集。  
3. 强制使用预处理语句：启用PDO::ATTR_EMULATE_PREPARES=false，杜绝SQL拼接路径。  
4. 服务端校验编码：在接收请求后立即验证Content-Type及GET/POST参数是否符合预期编码，异常则拒收。  
5. 数据库最小权限：Web应用数据库账户禁用LOAD_FILE、INTO OUTFILE等高危操作权限，限制注入危害面。  
6. 中间件加固：Nginx/Apache配置AddDefaultCharset utf-8，避免响应头缺失导致浏览器自主编码猜测。
