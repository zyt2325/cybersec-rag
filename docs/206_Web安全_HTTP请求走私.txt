HTTP请求走私

一、基本概念  
1. HTTP请求走私是一种利用前后端服务器对同一HTTP请求解析不一致导致的中间件绕过攻击。  
2. 攻击者通过构造特殊请求，使前端代理（如负载均衡器）与后端应用服务器对请求边界识别不同。  
3. 该漏洞不依赖服务端代码缺陷，而是源于HTTP协议实现差异及配置不当。  
4. 常见于使用HTTP/1.1且部署了反向代理、CDN或WAF的Web架构中。  
5. 其核心危害在于请求混淆，可导致缓存投毒、会话劫持、权限越界等连锁风险。

二、原理与关键机制  
1. 前后端对Content-Length和Transfer-Encoding头的优先级处理存在分歧：RFC 7230规定Transfer-Encoding优先级高于Content-Length，但部分服务器忽略此规则。  
2. 当请求同时包含合法Content-Length和被忽略的Transfer-Encoding: chunked时，前端可能按chunked解析，后端按Content-Length截断。  
3. 后端将本应属于下一个请求的数据误认为当前请求的body或后续请求起始，造成请求流错位。  
4. 代理服务器若未严格校验或规范化请求头（如合并、删除、重写Transfer-Encoding），会加剧解析歧义。  
5. HTTP/2与HTTP/1.1网关转换过程中，若未正确映射流控语义，也可能诱发走私条件。

三、典型类型与常见问题  
1. CL.TE型：前端按Content-Length处理，后端按Transfer-Encoding: chunked解析，导致后续字节被当作新请求。  
2. TE.CL型：前端按Transfer-Encoding解析，后端按Content-Length截断，使恶意数据滞留缓冲区并污染下个请求。  
3. TE.TE型：前后端均支持Transfer-Encoding，但对分块编码格式（如空格、大小写、多余头字段）解析不一致。  
4. 常见诱因包括代理禁用或错误处理TE头、后端禁用chunked解码、启用不安全的请求头转发。  
5. 某些CDN（如早期Cloudflare）或WAF（如ModSecurity默认配置）曾因头处理逻辑缺陷引入此类风险。  
6. 无法通过常规扫描器稳定检出，需结合响应延迟、状态码异常、缓存行为变化等手工验证。

四、防御措施与实践建议  
1. 前端代理应统一禁用Transfer-Encoding头（除明确需要的场景），或强制规范化为标准格式并移除歧义字段。  
2. 后端服务器必须严格遵循RFC 7230：收到含Transfer-Encoding的请求时，忽略Content-Length并完整处理分块。  
3. 在代理与后端间启用HTTP/2直连，避免HTTP/1.1解析不一致；若必须使用HTTP/1.1，应部署协议一致性校验模块。  
4. 禁止代理转发未经校验的TE、CL、Connection等敏感头字段，对非法组合（如CL+TE）直接拒绝请求。  
5. Web应用层应实施请求正则化：统一标准化请求头顺序、大小写及空白符，减少解析路径差异。  
6. 对所有入站请求执行深度协议合规性检查，例如检测分块编码语法错误、CL值与实际body长度偏差超阈值即拦截。
