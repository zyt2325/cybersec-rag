渗透测试流程规范

一、基本概念  
1. 渗透测试是经授权模拟真实攻击，评估目标系统安全防护能力的结构化技术活动。  
2. 必须签署书面授权协议，明确测试范围、时间窗口、禁止行为及数据处理要求。  
3. 遵循最小影响原则，避免对生产环境造成服务中断、数据损坏或性能显著下降。  
4. 测试全程需留存完整审计日志，包括操作时间、工具调用、发现证据及响应动作。  
5. 所有发现漏洞必须验证真实性与可利用性，禁止仅依赖扫描器告警直接定级。  

二、原理与关键机制  
1. 基于攻击链模型（如Kill Chain或MITRE ATT&CK），分阶段覆盖侦察、武器化、投递、利用等环节。  
2. 采用灰盒测试模式时，可获取部分架构文档或账户权限，但不提供源码或密钥等核心资产。  
3. 漏洞验证需复现触发条件并确认可控影响，例如内存破坏类漏洞需证明EIP/RIP可被劫持。  
4. 权限提升验证须区分本地提权与横向移动，明确凭证重用、令牌窃取等具体路径。  
5. 数据外泄检测依赖网络流量镜像与端点日志交叉分析，而非仅依赖边界防火墙日志。  

三、典型类型与常见问题  
1. 黑盒测试易遗漏业务逻辑缺陷，因缺乏接口文档导致API参数探测覆盖不全。  
2. 白盒测试若未隔离开发环境，静态分析可能误报第三方库已知漏洞（CVE编号匹配但补丁已应用）。  
3. 无线渗透中WPA3-SAE握手捕获失败常因客户端启用抗降级保护（如Dragonblood缓解措施）。  
4. 工控系统渗透受限于协议解析能力，Modbus/TCP功能码滥用易触发设备看门狗复位。  
5. 云环境测试常混淆责任共担模型，误将S3存储桶权限错误归因为客户配置而非AWS默认策略。  

四、防御措施与实践建议  
1. 建立渗透测试准入清单，强制要求提供WAF规则快照、IDS签名版本及网络拓扑图。  
2. 生产环境部署蜜罐诱捕节点，与真实资产隔离，用于识别未授权测试行为并触发告警。  
3. 对Web应用实施运行时应用自保护（RASP），实时阻断SQLi/XSS载荷执行而非仅记录。  
4. 关键系统启用内存安全编译选项（如GCC的-fstack-protector-strong与ASLR强制开启）。  
5. 渗透报告须按CVSS 3.1标准量化评分，并附带修复验证方法（如curl命令验证补丁有效性）。  
6. 组织每年至少开展两次红蓝对抗演练，蓝队需基于渗透报告更新SOC检测规则与EDR响应剧本。
