模板注入SSTI

一、基本概念  
1. 服务端模板注入（SSTI）指攻击者向服务端模板引擎输入恶意模板代码，导致其被意外执行的安全漏洞。  
2. 本质是模板引擎将用户可控数据误当作模板语法解析并执行，突破了数据与逻辑的隔离边界。  
3. 区别于客户端模板注入（CSTI），SSTI发生在服务端，可直接触发任意代码执行或敏感信息泄露。  
4. 常见于使用Jinja2、Twig、FreeMarker、Thymeleaf、Velocity等动态模板引擎的Web应用中。  
5. 漏洞成因多源于开发者未对用户输入做模板上下文隔离，直接拼接进模板字符串或调用render函数。

二、原理与关键机制  
1. 模板引擎在渲染阶段会解析特殊语法（如{{}}、{%%}）并执行其中表达式或语句。  
2. 当用户输入未经过滤进入模板渲染流程时，引擎将其识别为合法模板指令并求值。  
3. 某些引擎默认暴露运行时对象（如Python的__import__、globals()、mro()），构成代码执行链路。  
4. 对象属性遍历机制（如obj.attr.subattr）可被滥用访问内置类、模块及构造器，实现沙箱逃逸。  
5. 模板沙箱若配置不当（如禁用策略不完整、白名单过宽），无法阻止危险操作的执行。

三、典型类型与常见问题  
1. 表达式注入：用户控制{{}}内内容，如{{7*7}}返回49，进一步可调用危险方法。  
2. 语句注入：利用{%%}块执行赋值、循环、导入等语句，如{% import os %}{{os.popen('id').read()}}。  
3. 沙箱绕过：通过获取类对象（如"".__class__.__mro__[1].__subclasses__()）定位危险类并实例化。  
4. 日志/错误页面泄露：调试模式下模板异常堆栈可能暴露引擎类型、版本及对象结构，辅助利用。  
5. 二次渲染漏洞：后端将用户输入先存入数据库，后续作为模板参数再次渲染，形成延迟注入点。

四、防御措施与实践建议  
1. 严格禁止将任何用户输入直接拼接进模板字符串，必须通过安全的上下文变量传入。  
2. 使用模板引擎提供的自动转义功能，并确保其对所有输出位置（HTML、JS、CSS、URL）启用。  
3. 禁用高危内置对象和方法：在Jinja2中设置undefined=StrictUndefined，禁用__debug__、__import__等全局名。  
4. 实施最小权限沙箱：通过沙箱环境限制可访问模块（如仅允许datetime、json），禁用文件系统和网络操作。  
5. 避免在生产环境启用调试模式、模板热重载或详细错误回溯，防止敏感信息泄漏。  
6. 对模板渲染入口进行输入校验：采用白名单机制限制变量名、属性路径长度及嵌套深度。
