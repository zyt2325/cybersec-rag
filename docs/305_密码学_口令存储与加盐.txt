口令存储与加盐

一、基本概念  
1. 口令存储指系统将用户输入的口令经处理后持久化保存于数据库或配置文件中的过程。  
2. 明文存储口令是严重安全缺陷，一旦数据库泄露，所有账户立即失陷。  
3. 哈希函数是单向不可逆数学变换，将任意长度输入映射为固定长度摘要，用于替代明文存储。  
4. 加盐是在哈希计算前将随机生成的唯一字符串（salt）与口令拼接，再进行哈希运算。  
5. salt必须与哈希值一同存储，且每个用户对应独立salt，不可复用或全局统一。  

二、原理与关键机制  
1. 加盐的核心目标是破坏彩虹表攻击的有效性，使预计算哈希表失效。  
2. salt需具备密码学随机性，应使用CSPRNG（如/ dev/urandom或CryptGenRandom）生成。  
3. salt长度建议≥16字节（128位），过短易被暴力穷举覆盖。  
4. 哈希算法须采用抗碰撞性强、计算成本高的专用口令哈希函数（如Argon2、scrypt、bcrypt、PBKDF2）。  
5. 迭代轮数或内存/时间成本参数必须随硬件演进动态调高，防止算力提升导致离线破解加速。  

三、典型类型与常见问题  
1. 未加盐的MD5/SHA-1哈希仍广泛存在于老旧系统中，极易被彩虹表批量破解。  
2. 使用固定salt或用户名作为salt等同于无盐，无法抵御针对同一salt的批量攻击。  
3. 将salt硬编码在代码中或全局配置里，违背salt的用户粒度唯一性原则。  
4. 采用快速通用哈希（如SHA-256）直接哈希口令，缺乏计算延时，利于GPU/ASIC暴力破解。  
5. salt与哈希值以明文形式共存于同一数据库字段，虽不影响安全性，但易因开发误操作导致salt泄露路径扩大。  

四、防御措施与实践建议  
1. 强制使用现代口令哈希方案：优先选择Argon2id（v1.3+），其次为bcrypt（cost≥12）或PBKDF2-SHA256（迭代≥600,000轮）。  
2. salt必须每次注册/修改口令时全新生成，长度≥16字节，存储格式推荐Base64编码并与哈希值用分隔符合并（如$argon2id$v=19$m=65536,t=3,p=4$c2FsdDEyMzQ=$...）。  
3. 禁止自研哈希逻辑，使用经FIPS认证或OWASP推荐的成熟库（如libsodium、Python passlib、Java Spring Security Crypto）。  
4. 数据库权限严格分离，口令哈希表仅限认证服务读取，禁止应用层直接访问或日志输出哈希字段。  
5. 定期审计口令存储实现：检查salt生成方式、哈希算法版本、参数强度及是否启用密钥派生函数的内存/并行度防护。  
6. 对遗留系统实施渐进式迁移：新增用户强制新方案；存量用户在下次登录时重哈希升级，避免批量重算引发服务阻塞。
