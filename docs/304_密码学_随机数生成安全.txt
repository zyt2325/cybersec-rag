随机数生成安全

一、基本概念  
1. 密码学安全随机数生成器（CSPRNG）是满足不可预测性、不可重现性和统计随机性的专用随机源。  
2. 真随机数（TRNG）依赖物理熵源（如电子噪声、时钟抖动），输出不可算法推导。  
3. 伪随机数生成器（PRNG）通过确定性算法扩展种子，若种子可预测则整个序列可被复现。  
4. 熵是衡量随机性质量的核心指标，低熵种子会导致密钥空间大幅收缩，易遭暴力或状态恢复攻击。  
5. 随机数在密钥生成、非对称密钥对创建、会话令牌、初始化向量（IV）等场景中直接决定系统安全性边界。

二、原理与关键机制  
1. CSPRNG必须通过前向安全性设计：即使内部状态被泄露，历史输出仍不可逆推。  
2. 种子必须源自高熵源，Linux使用/dev/random和/dev/urandom混合硬件中断、内存状态等熵池数据。  
3. 混合机制要求定期重注入熵，避免长期运行后熵耗尽导致输出退化为确定性序列。  
4. NIST SP 800-90A标准定义了DRBG（确定性随机比特生成器）三类算法：Hash_DRBG、HMAC_DRBG、CTR_DRBG，均需通过状态更新与再散列保障抗碰撞性。  
5. 输出函数须具备抗输出恢复能力：已知部分输出无法反推内部状态或未输出比特。

三、典型类型与常见问题  
1. 使用time()或getpid()等低熵值作为PRNG种子，导致密钥可被时间窗口内穷举。  
2. Java SecureRandom在早期版本中未正确绑定操作系统熵源，JVM启动时熵不足引发重复密钥。  
3. OpenSSL在某些嵌入式环境因缺乏/dev/random支持而回退至弱熵初始化，造成RSA私钥可预测。  
4. Web应用用Math.random()生成密码重置令牌，该函数非密码学安全且V8引擎存在可预测性漏洞。  
5. 嵌入式设备缺少硬件随机数发生器（HRNG），依赖软件熵收集效率低下，熵池长期低于256位阈值。

四、防御措施与实践建议  
1. 优先调用操作系统提供的CSPRNG接口：Linux用getrandom(2)系统调用，Windows用BCryptGenRandom，避免自行实现。  
2. 在密钥生成前验证熵池可用性，如Linux检查/proc/sys/kernel/random/entropy_avail是否≥256。  
3. 对于无OS环境（如MCU），必须集成经FIPS 140-2认证的硬件TRNG模块，并启用实时熵健康检测。  
4. 禁止将非密码学PRNG（如Mersenne Twister）用于安全上下文；TLS 1.3明确禁止使用RC4、MD5等弱随机组件。  
5. 容器化部署时需确保宿主机熵源透传，Docker默认不共享/dev/random，应挂载hostPath或配置rng-tools服务。  
6. 审计代码中所有随机数调用点，使用静态分析工具（如Semgrep规则cryptography-insecure-random）识别Math.random()、rand()等危险调用。
