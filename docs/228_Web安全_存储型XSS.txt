存储型XSS

一、基本概念  
1. 存储型XSS指恶意脚本被永久保存在目标服务器（如数据库、消息论坛、用户评论区）中，后续用户访问相关页面时自动执行。  
2. 与反射型XSS不同，其攻击载荷不依赖URL参数传递，而是通过服务端持久化存储触发，影响范围更广、持续时间更长。  
3. 典型场景包括博客评论、用户资料编辑、工单系统、CMS后台内容管理等需用户输入并展示的交互功能。  
4. 攻击成功后，脚本在受害者浏览器上下文中运行，可窃取Cookie、会话令牌、键盘记录或发起CSRF操作。  

二、原理与关键机制  
1. 服务端未对用户提交内容进行充分过滤或转义，直接将未经处理的数据写入持久化存储（如MySQL、MongoDB）。  
2. 前端渲染时直接使用innerHTML、document.write或Vue/React中v-html、dangerouslySetInnerHTML等危险API插入服务端返回的数据。  
3. 浏览器解析HTML时将存储的恶意标签（如<script>、<img onerror=...>）识别为可执行代码并执行。  
4. 脚本执行环境继承当前页面的Origin、Cookie和权限，具备完整DOM访问能力及同源AJAX请求权限。  

三、典型类型与常见问题  
1. 普通脚本注入：提交<script>alert(1)</script>，服务端存入后所有查看者弹窗。  
2. 事件处理器注入：利用onload、onerror、onfocus等HTML事件属性触发无script标签的执行。  
3. 编码绕过：提交Unicode编码、HTML实体编码（如&#x3C;script&#x3E;）或大小写混合标签规避简单黑名单过滤。  
4. 富文本场景风险：WYSIWYG编辑器若未严格限制标签白名单（如允许iframe、javascript:协议），易引入存储型XSS。  
5. 后台管理界面漏洞：管理员审核评论或编辑用户资料时，未对预览/渲染内容做二次输出编码，导致管理员账户被劫持。  

四、防御措施与实践建议  
1. 输出编码：在HTML上下文渲染用户数据前，对特殊字符进行HTML实体编码（< → &lt;，> → &gt;，" → &quot;等）。  
2. 内容安全策略（CSP）：配置strict-dynamic策略，禁用内联脚本与eval，并指定可信脚本源，降低XSS危害。  
3. 输入验证与白名单过滤：对富文本使用成熟库（如DOMPurify）进行服务端净化，仅保留安全标签与属性。  
4. 使用安全框架特性：优先采用React的默认转义机制、Vue的v-text指令，避免显式使用v-html；后端模板引擎启用自动转义（如Jinja2 autoescape）。  
5. 敏感操作二次验证：修改密码、转账等关键操作强制重新输入密码或使用WebAuthn，防止XSS窃取会话后越权执行。  
6. 设置HttpOnly Cookie：阻止JavaScript读取会话Cookie，显著降低XSS导致的会话劫持风险。
