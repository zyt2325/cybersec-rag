供应链投毒攻击

一、基本概念  
1. 供应链投毒攻击指攻击者通过篡改软件开发、分发或依赖引入环节中的合法组件，向目标系统植入恶意代码的行为。  
2. 投毒对象包括开源包仓库（如PyPI、npm）、构建工具链（如CI/CD配置文件）、第三方SDK、镜像仓库（如Docker Hub）及固件更新服务器。  
3. 攻击不直接入侵最终用户系统，而是利用开发者对上游依赖的信任关系实现横向渗透与隐蔽持久化。  
4. 区别于传统漏洞利用，其危害具有放大效应：单个被污染组件可影响成千上万下游项目与终端用户。  

二、原理与关键机制  
1. 依赖混淆：攻击者上传同名但版本号更高的恶意包（如将package-name-1.0.0替换为package-name-100.0.0），诱导构建工具自动拉取。  
2. 账户劫持：通过钓鱼、凭证复用或API密钥泄露获取开源包维护者账户权限，直接发布含后门的新版本。  
3. 构建过程劫持：篡改项目根目录下的build.gradle、Makefile或.github/workflows/*.yml等文件，在编译阶段注入恶意指令。  
4. 镜像层污染：在Dockerfile中指定受控基础镜像，或向公开镜像仓库推送含恶意启动脚本的伪造标签（如:latest）。  

三、典型类型与常见问题  
1. 开源包投毒：2022年UA-Parser-js事件中，攻击者劫持npm包发布含CoinMiner的0.7.22版本，影响超5000个项目。  
2. CI/CD流水线投毒：修改GitHub Actions workflow文件，使每次构建均执行远程shell脚本并回传环境变量。  
3. 依赖传递性风险：项目仅直接引用A库，但A依赖B，B又依赖被投毒的C库，导致间接感染且难以溯源。  
4. 版本锁定缺失：未在requirements.txt或package-lock.json中固定次版本号，导致自动升级至恶意新版本。  
5. 无签名验证：下载二进制依赖时未校验GPG签名或SBOM（软件物料清单）哈希值，无法识别内容篡改。  

四、防御措施与实践建议  
1. 实施最小权限原则：CI/CD服务账号禁用写权限，包发布密钥使用硬件安全模块（HSM）或云KMS托管。  
2. 启用依赖完整性保护：在pip中配置--require-hashes，npm中启用audit-resolve，强制校验每个包的SHA512摘要。  
3. 建立可信源白名单：通过私有仓库代理公共源（如Nexus Repository），仅允许经静态扫描与人工审核的包入库。  
4. 集成SBOM生成与比对：构建时自动生成SPDX或CycloneDX格式清单，上线前与基线SBOM做差异分析。  
5. 对关键构建步骤实施隔离：在独立网络域运行CI节点，禁止其访问互联网，所有依赖须经离线缓存同步。  
6. 定期轮换凭证与审计日志：对包注册平台API密钥实行90天强制轮换，并留存所有publish操作的完整审计轨迹。
