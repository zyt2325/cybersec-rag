API接口安全

一、基本概念  
1. API接口是应用程序间标准化的数据交互通道，常见类型包括RESTful、GraphQL、SOAP等。  
2. 接口安全指保障API在身份认证、数据传输、访问控制等环节不被未授权访问或篡改。  
3. API资产常暴露于公网，且调用频次高、业务逻辑深，成为攻击者重点目标。  
4. 与Web前端不同，API通常无会话状态、依赖Token而非Cookie，安全边界更依赖服务端策略。  
5. OpenAPI规范虽提升可读性，但也可能被攻击者用于自动化接口测绘与攻击面分析。

二、原理与关键机制  
1. 身份认证依赖OAuth 2.0、JWT、API Key等机制，其中JWT需校验签名、过期时间及iss/aud字段。  
2. 授权采用基于角色（RBAC）或属性（ABAC）的细粒度策略，避免过度赋权导致横向越权。  
3. 传输层强制使用TLS 1.2+加密，禁用HTTP明文通信及弱密码套件（如RC4、SHA-1）。  
4. 请求限流通过令牌桶或漏桶算法实现，按客户端IP、API Key或用户ID维度独立计数。  
5. 输入验证需在服务端执行，对JSON Schema、GraphQL查询深度与复杂度实施硬性约束。

三、典型类型与常见问题  
1. Broken Object Level Authorization（BOLA）：通过篡改ID参数绕过资源归属校验，访问他人数据。  
2. Excessive Data Exposure：服务端未按权限裁剪响应字段，返回敏感信息如密码哈希或身份证号。  
3. Injection类漏洞：SQL、NoSQL、OS命令注入仍存在于未参数化处理的动态查询中。  
4. Mass Assignment：客户端提交未预期字段（如is_admin=true），服务端盲目绑定至对象引发提权。  
5. Insecure Direct Object References（IDOR）：使用可预测标识符（如递增整数）且无服务端所有权校验。

四、防御措施与实践建议  
1. 实施API网关统一管控认证、限流、日志与WAF规则，避免安全逻辑分散到各微服务。  
2. 对所有API进行最小权限设计，响应数据按用户角色动态过滤，禁用全局通配符授权。  
3. JWT签发时设置短有效期（≤15分钟），配合Refresh Token机制，并在Redis中维护失效黑名单。  
4. 使用OpenAPI 3.0定义接口并启用Schema校验中间件，拒绝不符合格式或字段类型的请求体。  
5. 定期执行API渗透测试，覆盖越权、业务逻辑缺陷及第三方组件漏洞（如Log4j在API服务中的使用）。  
6. 记录完整审计日志，包含客户端IP、API Key哈希、操作时间、资源路径及响应状态码，保留≥180天。
