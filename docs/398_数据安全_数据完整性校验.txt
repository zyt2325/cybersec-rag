数据完整性校验

一、基本概念  
1. 数据完整性校验是指验证数据在传输或存储过程中未被意外损坏或恶意篡改的技术手段。  
2. 核心目标是确保接收方获得的数据与发送方原始数据完全一致，具备可验证的“未变更”属性。  
3. 它不提供机密性或可用性保障，仅聚焦于数据内容的准确性和一致性。  
4. 是CIA三元组（机密性、完整性、可用性）中完整性维度的实现基础。  
5. 常用于软件分发、固件升级、数据库事务日志、API通信等关键场景。

二、原理与关键机制  
1. 通过单向密码学函数（如SHA-256、SHA-3）生成固定长度摘要值，原始数据微小变化将导致摘要显著不同（雪崩效应）。  
2. 发送方计算数据摘要并随数据一同传输；接收方重新计算摘要并与接收到的摘要比对，一致则判定完整。  
3. 数字签名在摘要基础上叠加非对称加密（如RSA-SHA256），既验证完整性又实现身份认证与不可否认性。  
4. 校验过程依赖密钥管理：HMAC需共享密钥，而数字签名依赖私钥保密性与公钥可信分发。  
5. 摘要本身不加密数据，因此无法防止窃听，仅防范篡改与损坏。

三、典型类型与常见问题  
1. 简单校验和（如CRC32）计算快但抗碰撞性弱，易被针对性构造篡改绕过，不适用于安全场景。  
2. 密码学哈希（如SHA-1）已遭理论碰撞攻击，NIST明确禁止在数字签名等安全用途中使用。  
3. HMAC因引入密钥增强抗碰撞性，但若密钥复用或长度不足（<128位），可能遭受长度扩展攻击。  
4. Merkle树支持大规模数据分块校验与高效局部验证，但树结构本身需可信根哈希保护。  
5. 若校验值与原始数据同信道传输且未受保护（如明文HTTP返回JSON+MD5），攻击者可同步篡改二者。

四、防御措施与实践建议  
1. 优先选用FIPS 140-2/3认证的哈希算法（如SHA-256、SHA-384），禁用MD5、SHA-1及弱哈希变体。  
2. 对高敏感数据实施数字签名而非单纯哈希，私钥须存储于HSM或TEE中，杜绝明文导出。  
3. 校验值必须通过独立可信信道传输（如HTTPS响应头携带Signature，或由PKI证书链验证的单独签名文件）。  
4. 在固件更新、容器镜像拉取等场景强制启用签名验证策略（如Docker Content Trust、UEFI Secure Boot）。  
5. 应用层需校验服务端返回的完整性字段（如HTTP的Digest头、ETag），拒绝无校验或校验失败的响应。  
6. 日志系统采用写时哈希（如HMAC-SHA256 over log entry + timestamp + previous hash）构建防篡改链式结构。
