SSRF服务端请求伪造  
一、基本概念  
1. SSRF（Server-Side Request Forgery）是一种由服务端发起非预期网络请求的安全漏洞。  
2. 攻击者通过操控应用接收的用户输入，诱使后端服务器向内网或受限地址发起HTTP或其他协议请求。  
3. 该漏洞本质是服务端未对用户可控的URL参数进行严格校验与限制。  
4. SSRF常被用于突破网络边界，探测内网拓扑、访问元数据服务或中继攻击其他系统。  
5. 与CSRF不同，SSRF发生在服务端而非客户端，利用的是服务端的信任关系和网络权限。  

二、原理与关键机制  
1. 应用在功能中需代理用户请求（如图片加载、网页预览、Webhook回调），但未校验目标URL的协议、域名、IP及端口。  
2. 服务端使用通用HTTP客户端（如cURL、Requests、HttpURLConnection）发起请求，且默认支持file://、gopher://、dict://等非HTTP协议。  
3. 内网服务（如Redis、Elasticsearch、Metadata API）缺乏身份认证或仅依赖网络隔离，易被SSRF直接访问。  
4. DNS重绑定攻击可绕过基于域名的白名单校验，使同一域名解析为不同IP（公网→内网）。  
5. URL解析歧义（如@符号、302跳转、IPv6双冒号缩写）可能导致校验逻辑与实际请求目标不一致。  

三、典型类型与常见问题  
1. 基础SSRF：直接读取本地文件（file:///etc/passwd）或访问127.0.0.1:8080等内网服务。  
2. 协议混淆型：利用gopher://构造Redis命令或SMTP交互，实现命令执行或信息泄露。  
3. 云环境特有风险：AWS/Azure/GCP元数据接口（如169.254.169.254）常暴露敏感凭证，成为高危目标。  
4. DNS解析延迟导致的绕过：校验时解析为合法域名，请求时DNS缓存已更新为恶意内网IP。  
5. 后端服务响应内容未过滤：返回的内网服务响应（如Redis INFO）可能包含敏感配置或密钥。  
6. 无回显SSRF：虽无直接响应，但可通过时间盲注（如带外带宽探测）或错误日志间接验证。  

四、防御措施与实践建议  
1. 禁止使用用户输入直接拼接URL；必须使用白名单机制校验协议、域名、IP段和端口。  
2. 显式禁用危险协议（file://、gopher://、dict://、ftp://），仅允许HTTP/HTTPS并限制重定向次数。  
3. 对URL进行标准化处理（去除空格、编码、@符号、跳转）后再校验，避免解析歧义。  
4. 使用权威DNS解析并缓存结果，禁止递归解析；校验IP时须进行真实IP转换（处理X-Forwarded-For伪造）。  
5. 内网服务应启用强身份认证，禁用匿名访问；云平台元数据服务需配置IMDSv2或网络ACL限制。  
6. 在网络层部署微隔离策略，限制应用服务器对内网非必要端口的出向连接，缩小攻击面。
